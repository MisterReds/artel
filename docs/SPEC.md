# ТЗ Artel v2 — для исполнителя

Основание: docs/ORCHESTRATION.md, docs/AUTONOMY.md, docs/TARGET_ARCHITECTURE.md; замеры кода от 2026-10-17
(59 модулей, 17,2 тыс. строк, 399 тестов, 24 скрытых цикла импортов, 19 глобальных изменяемых объектов).

## 1. Intent и критерии успеха

**Intent.** Человек пишет идею одной фразой. Artel на его подписке (Claude Code и/или Codex) часами доводит её до
результата, который проверен независимо, не упираясь в лимит дорогой модели. Человек в любой момент видит, что
происходит и почему, и может вмешаться.

**Цель за целью.** Владелец перестаёт быть оператором агентов и становится заказчиком: тратит минуты на
постановку и приёмку, а не часы на сопровождение.

Проверяемые утверждения (все измеряются командой `artel metrics <проект>` по журналу событий):

| # | Утверждение | Метрика | Порог | Как мерить |
|---|---|---|---|---|
| U1 | Из сырой идеи — проверенный результат | все критерии Intent подтверждены | 100% критериев; гейты зелёные | вердикт Critic'а **другого провайдера** + гейты; без ручной правки результата |
| U2 | Долгий горизонт | часов непрерывной работы | ≥ 6 ч на тесте L без остановки по лимиту | от `run/start` до `done`; остановок `limit` = 0 (деградация допустима) |
| U3 | Экономия дорогой модели | доля токенов и доля вызовов дорогого профиля | ≤ 5% токенов, ≤ 5% вызовов | `tier/usage`, `agent/end` |
| U4 | Эффективность | токены на принятую задачу | ≤ 0,7 × базовой линии (поставка 0) | все токены / принятые задачи |
| U5 | Автономия | доля шагов без вопроса человеку | ≥ 95%; вмешательств ≤ 1 + обязательные подтверждения | события `owner/*` |
| U6 | Прозрачность | у каждого решения менеджера есть «зачем» и «что дальше» | 100% записей Decision Log | проверка схемы журнала |
| U7 | Независимость от провайдера | тест S проходит на двух провайдерах и с локальной моделью в роли Executor | 3 из 3 | три прогона одного сценария |
| U8 | Честная архитектура | циклы импортов, глобальное состояние, вендор в логике | 0 / 0 / 0 вне `adapters/` и конфига | `scripts/archcheck.py` в CI |

## 2. Приоритеты и что вырезать

Правило: при конфликте побеждает меньший номер. Задача, не продвигающая пункт 1, ждёт его прохождения.

1. Приёмочный тест «идея → результат» на реальной подписке проходит.
2. Долгий горизонт: U2.
3. Экономия дорогой модели: U3, U4.
4. Автономия с прозрачностью и управлением: U5, U6.
5. Независимость от провайдера: U7.
6. Честная архитектура: U8.
7. Переписывание неверного — инструмент для 1–6, а не цель.

## 3. Решение о переписывании

**Решение: переписать по docs/TARGET_ARCHITECTURE.md, методом «душителя».**

Обоснование:
- God-объекты (`Manager` 937 строк, `Evolution` 1224), четыре копии цикла CLI, 24 скрытых цикла и вендор в логике —
  свойство конструкции, а не отдельные дефекты.
- Пункты 4–5 (Intent, режимы, журнал, откат, роутинг по профилям) требуют одного места, где меняется поток. Сейчас
  его нет.
- Полная замена за раз остановила бы продукт. «Душитель» держит его рабочим на каждом шаге.

**Сохраняется:**
- смысл и контракты: Intent, Task Contract, схемы, канбан (SQLite) как адаптер;
- журнал событий;
- навыки, политика команд, песочница, worktree-изоляция;
- 399 тестов поведения;
- дашборд и Telegram как приложения.

**Заменяется:**
- `Manager.run` → FSM + `Orchestrator`;
- рантаймы CLI → `AgentPort` с одним циклом и кодеками;
- `routing.py`, `limits.py`, цены → каталог моделей и Capability Profiles в конфиге;
- web-handler → маршруты над оболочкой;
- глобальные кэши → объекты с владельцем через DI.

**Порядок миграции:** базовая линия → удаление лишнего → контракты и порты → адаптеры (параллельно) → FSM →
журнал и управление → приложения → повторный приёмочный тест. Старый модуль удаляется в той же поставке, где новый
прошёл те же тесты.

## 5. Приёмочный тест «сырая идея → результат»

**Сценарии** (идея вводится одной фразой, без подсказок):
- **S (короткий, ~1 ч):** «Сделай CLI-утилиту, которая из выписок банка в CSV собирает расходы по категориям в
  SQLite и строит HTML-отчёт за месяц».
- **L (длинный, ≥ 6 ч):** «Сделай веб-приложение учёта домашних расходов: импорт CSV разных банков, автокатегории
  с обучением на правках пользователя, бюджеты с предупреждениями, отчёты, тесты, инструкция по развёртыванию».

**Окружение:** машина владельца, `artel web` запущен, подписка Claude Code (обязательно) и Codex (для независимого
Critic'а), Telegram привязан. В облачной сессии исполнителя длинный тест не проводится: её фоновые задачи живут 2 ч.

**Шаги:**
1. Чистый `ARTEL_HOME`; `artel update`; записать версию.
2. Ввести идею в дашборд.
3. Владелец подтверждает Intent — единственное плановое вмешательство.
4. Дальше без вмешательства, кроме обязательных подтверждений (необратимое, публикации).
5. По завершении — `artel metrics <проект> --json` и вердикт Critic'а другого провайдера по критериям Intent.
6. Владелец запускает результат по инструкции из проекта — внешнее подтверждение U1.

**Метрики:** все из таблицы §1, плюс:
- стоимость по провайдерам (API — $, подписки — токены);
- доля переписанного кода: строки в новом макете / все строки, по `git`;
- стоимость переписывания: сумма дорогих токенов главной сессии по поставкам, из журнала сессий.

**Пройден**, если S и L выполняют U1–U6, а S дополнительно выполняет U7.

**Провал и действия:**

| Провал | Действие |
|---|---|
| U1 | разбор журнала: на каком переходе потеряна цель → задача в ближайшую поставку |
| U2 | найти причину остановки (лимит, сбой, зависание) → исправить до повторного прогона |
| U3/U4 | профиль вызовов: какая роль ест дорогой бюджет → ужать её бриф или понизить профиль |
| U5 | каждое вмешательство классифицировать: нужное (оставить) / лишнее (убрать правило) |
| два провала подряд по одной метрике | эскалация владельцу с Rewrite Proposal для виновного модуля |

## 6. Контракты поставок

**П0. Приёмочный стенд**
- Вход: текущий master.
- Выход:
  - `artel metrics` — все метрики §1 и §5 из журнала событий;
  - сценарии S и L в `bench/acceptance/`;
  - отчёт базовой линии: S на текущем коде у владельца.
- Ограничения: код продукта не меняется, кроме недостающих событий для метрик.
- Проверка: метрики на записанном журнале совпадают с ручным подсчётом; тест на синтетическом журнале.

**П1. Удаление**
- Вход: список §2.
- Выход: кода, тестов, настроек и UI этих компонентов нет; README исправлен.
- Ограничения: остальные тесты зелёные.
- Проверка: `grep` по именам пуст; полный набор тестов.

**П2. Контракты и порты**
- Вход: схемы §6 TARGET_ARCHITECTURE.
- Выход: `artel/contracts/` (frozen-данные с валидацией), `artel/ports/` (LLMPort, AgentPort, MemoryPort, EventPort,
  ToolPort, ClockPort, ConfigPort), fake-адаптеры.
- Ограничения: никаких импортов из `adapters`, сети, файлов в `contracts` и `ports`.
- Проверка: юнит-тесты схем; archcheck на эти пакеты.

**П3. AgentPort**
- Вход: поведение рантаймов claude_code и codex (их тесты), контракт AgentPort.
- Выход: `adapters/agent/loop.py` (мост, зеркало событий, продолжение, политика, лимиты — один раз) + кодеки
  `claude_code.py`, `codex.py` по ≤ 200 строк; старые рантаймы удалены.
- Ограничения: секреты только по имени переменной; поведение песочницы и проверяющих ролей не меняется.
- Проверка: все тесты рантаймов; живой smoke у владельца: одна задача на каждой подписке.

**П4. LLMPort и каталог**
- Вход: `llm_providers`, `routing`, `limits`, таблица цен.
- Выход: `adapters/llm/{anthropic,openai_compat}`, каталог моделей и Capability Profiles в `artel.yaml`,
  `core.select_model` (чистая функция).
- Ограничения: ни одного имени модели или вендора вне `adapters/` и конфига.
- Проверка: одна роль на двух каталогах выбирает разные модели без правки кода; локальная модель через
  openai_compat проходит профиль Executor (тест с фейковым сервером + живой прогон у владельца).

**П5. archcheck**
- Вход: правила §10 TARGET_ARCHITECTURE.
- Выход: `scripts/archcheck.py` (циклы импортов, глобальное изменяемое состояние, вендор вне адаптеров, ядро без
  внешних импортов) + шаг CI.
- Ограничения: работает на `ast`, без сторонних зависимостей.
- Проверка: падает на подсаженных нарушениях, проходит на чистом макете.

**П6. FSM и Orchestrator**
- Вход: `Manager` и его тесты; таблица переходов §4 TARGET_ARCHITECTURE.
- Выход: `core/fsm.py` (`next_state`, таблица), `shell/orchestrator.py`, `shell/budget.py`; `manager.py` удалён.
- Команда растёт и вширь, и вглубь: задача адресуется профессии, свободный экземпляр забирает её из очереди
  профессии (`assignee` — пожелание); экземпляры одной профессии — клоны шаблона (общие SOUL, навыки, память
  профессии; свои worktree и черновая память). Решение «добавить / снять экземпляр, кому какую задачу» —
  чистая функция `core.schedule(state)`: добавить, если готовых задач профессии больше, чем свободных
  экземпляров, в пределах `max_parallel`, `team.max_per_role` и бюджета; снять после простоя; мощность делится
  по спросу; клонируются только исполнители, рантайм в лимите не растёт; задачи, трогающие одни файлы, идут
  последовательно; ревьюер ≠ автор; каждое решение — в журнал решений с причиной.
- Ограничения: `Orchestrator` не принимает решений, только исполняет эффекты; ни один класс > 300 строк.
- Проверка: тест на каждый переход; все тесты поведения проекта; S-прогон на scripted-провайдере; при шести
  готовых задачах одной профессии и `max_parallel: 3` идут три одновременно, готовая задача не стоит при свободной
  мощности.

**П7. Intent, журнал, управление**
- Вход: intake, события, снимки.
- Выход:
  - Intent с версиями и подтверждением (дашборд и Telegram);
  - Decision Log;
  - пауза, откат шага, смена Intent, режимы автономии, бюджет из UI — как события FSM.
- Ограничения: необратимое и внешнее — только с подтверждением; «сделано» — только с идентификатором от внешней
  системы.
- Проверка:
  - сценарные тесты на каждую команду;
  - откат возвращает файлы к снимку побайтно;
  - журнал проходит проверку схемы (U6).
- Знания по уровням (MemoryPort): проект (`projects/<slug>/knowledge/`, агенты пишут только сюда) → общая
  библиотека (агентам только чтение) → навыки владельца. Правка общего навыка — локальная копия в проекте.
  Проект при старте фиксирует версию общей библиотеки (`skills.lock` с хэшами) и получает изменения только на
  своей границе. Продвижение в общую библиотеку — по доказательствам (успех в нескольких задачах или двух
  проектах), после проверки безопасности, Critic'а другого провайдера и регрессии бенча; политика, секреты,
  сеть и конфиг не продвигаются автоматически; конкретика проекта уходит наружу только обобщённым уроком.
  Навык, после продвижения которого растут сбои в разных проектах, уходит в карантин.
  Проверка: навык из проекта A не меняет поведение идущего проекта B; откат продвижения побайтно.

**П8. Приложения**
- Вход: `web/server.py`, `cli.py`, `telegram.py`.
- Выход: маршруты по файлам над API оболочки; приложения не импортируют ядро и адаптеры напрямую.
- Ограничения: интерфейс на русском; пользовательский и разработческий режимы сохранены.
- Проверка: тесты дашборда; скриншоты обоих режимов; archcheck.

**П10. Профили качества** (после П3, до П4)
- Вход: дефект с `rg` (проверка на отсутствующей утилите), аудит 2026-10 (у продуктов нет инженерных ворот),
  установка инструментов без `sudo` из П3.
- Выход:
  - каталог профилей `artel/data/quality/*.yaml` по типу результата (python, node/web, static, cli, document) и
    уровню (`prototype` | `production`); профиль = определение готовности: формат и линтер, типы, тесты с порогом
    покрытия, безопасность (статический анализ, аудит зависимостей, поиск секретов), зафиксированные зависимости,
    README с запуском, команда запуска результата, архитектурные правила (циклы импорта, слои), обработка ошибок;
  - определение типа и уровня: intake по цели, владелец может переопределить в проекте;
  - генератор проверок: проверки задач и финального аудита строятся из профиля, планировщик добавляет только
    проверки сути задачи; каждая программа проверки разрешается (`which`) или ставится до принятия плана;
  - чек-лист профиля у ревьюера и аудитора; для `production` — Critic другого провайдера;
  - метрики качества в `artel metrics` и отчёте приёмки;
  - дисциплина исправлений у воркеров и ревьюера: в задаче-исправлении сначала тест, воспроизводящий ошибку, его
    падающий вывод — в доказательствах сдачи; ревьюер отклоняет сдачу без него и тесты, которые прошли бы при
    «пустой» реализации (на уровне `production` — мутационный прогон по изменённым файлам); исправление, которое
    прячет сбой (повтор, пауза, ослабленная проверка), не принимается;
  - менеджер: «атакуй предпосылку» — после второго провала с той же причиной сначала проверяется предпосылка
    (окружение или работа), а не планируется третья попытка;
  - пороги профиля: CRAP < 10 на изменённую функцию, нет дублирования, мутанты без объяснения не выживают.
- Ограничения: строгость соразмерна цели (контенту не нужен pytest); профили — данные, не код; инструменты только
  из каталога с фиксированными версиями; ни одна проверка не ссылается на отсутствующую программу.
- Проверка:
  - на каждый профиль — эталонный маленький проект, который проходит, и испорченный, который не проходит
    (линтер, тест, секрет, цикл импорта);
  - задача, проверка которой требует отсутствующую утилиту, завершается без владельца;
  - сценарий S даёт продукт с чистым линтером, проходящими тестами и без серьёзных находок безопасности.

**П9. Приёмка v2**
- Вход: сценарии §5.
- Выход: отчёт с U1–U8 и сравнением с базовой линией.
- Проверка: пороги §1; вердикт Critic'а другого провайдера; запуск результата владельцем.
